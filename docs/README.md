Welcome to the central documentation index. This repository uses a topic-based documentation hierarchy to support software engineers and autonomous AI agents in maintaining clean, scalable, and resilient systems.

---

## 1. Documentation Authority & Conflict Resolution

When technical documents or code conflict, resolve authority in this strict precedence order:

1. **Applicable Law & Security Policy**: Mandatory regulatory, privacy, and organizational security policies.
2. **Effective Published Contracts**: Deployed API specifications, published integration events, and database persistence contracts.
3. **Accepted Architecture Decision Records (ADRs)**: Formal architecture decisions under [`adr/`](./adr/README.md) defining target state and migration plans.
4. **AI Guardrails & Engineering Standards**: Rules in [`AGENTS.md`](../AGENTS.md) and [`standards/`](./standards/README.md).
5. **Operational Runbooks & Guidelines**: Operational runbooks in [`operations/`](./operations/deployment.md).
6. **Existing Source Implementation**: Implementation details demonstrate compatibility constraints but are NOT automatic precedent for new designs.

*Note: An ADR defines migration intent, but does not retire an active published contract until consumer transition and deprecation milestones are satisfied.*

## 2. Document Classification & Metadata Standard

Every document under `docs/` carries an architectural classification and a lifecycle state:

### Document Classifications

| Tag | Classification | Meaning & Adoption Policy |
|---|---|---|
| `[CORE]` | Core Governance | Universal operational contract or primary gateway. Maintained and kept concise across projects. |
| `[STANDARD]` | Normative Standard | Universal applicability-driven engineering rule. Read on-demand; never loaded in full by default. |
| `[PROFILE]` | Repository Profile | Target repository fact or convention. Contains placeholders in baseline; MUST be replaced with verified project facts. |
| `[TEMPLATE]` | Reusable Blueprint | Core-listed blueprints are reusable reference candidates; additional templates require concrete need. Instances require separate exact approval. |
| `[DEFERRED]` | Conditional Artifact | Intentionally absent until concrete implementation contracts or visual assets exist. |
| `[GENERATED]` | Tool-Generated Output | Generated by automation; not a manually edited authority. |

### Document Lifecycle Metadata

All maintained Markdown documents under `docs/` SHOULD include a metadata block:

```markdown
> **Classification:** `[CORE | STANDARD | PROFILE | TEMPLATE | DEFERRED | GENERATED]`  
> **Status:** `Draft | Verified | Deprecated`  
> **Owner:** `<Owning Team / Role>`  
> **Last verified:** `<Date or Commit SHA>`  
> **Evidence:** `<Test suite, CLI output, or ADR reference>`
```

- **Draft**: Working or unverified document; placeholders present.
- **Verified**: Confirmed accurate against the active codebase and running tests.
- **Deprecated**: Superseded by a newer document or ADR.
- **Anti-Hallucination Rule**: Never advance `Last verified` unless the entire document scope was verified with executable evidence.

## 5. Adoption Guide for New and Existing Projects

This section and the adoption directory entry above are source-baseline routes, not permanent destination dependencies. Follow the [canonical lifecycle](./adoption/ai-implementation-workflow.md): exclude source-only adoption docs/commands in both scopes; adapt destination README/index/manifest copies to omit missing local routes or use verified accessible source links. Existing destination cleanup requires explicit per-file approval, ownership/drift checks, successful verification before cleanup, and final verification afterward. Preserve customized/user-owned files and report conflicts. Permanent fallback is in [`AGENTS.md`](../AGENTS.md) section 2.

Both new and existing projects default to `core-reference`; `full-reference` is explicit opt-in. The [canonical scope policy](../BASELINE.md) requires exact-file approval, never bulk recursive copy/mirror, and excludes Git metadata (file/directory/nested), plans, state and deferred source payloads. Preserve target root identity/history/license and record MIT attribution. Adapt this index to the selected destination tree, omitting absent topic routes while retaining AGENTS fallback; do not import extra docs merely to keep source links. Exclusion does not delete target artifacts or prohibit separately authorized later generation. Validate path overlap/containment, drift, duplicate mappings and actual changes against the manifest.

Detailed adoption playbooks are provided under [`adoption/`](./adoption/README.md):

- **New Project Initialization**: See [`adoption/new-project.md`](./adoption/new-project.md) (uses `/plan-new-project-adoption`).
- **Existing Project Integration**: See [`adoption/existing-project.md`](./adoption/existing-project.md) (uses `/plan-existing-project-adoption`).
- **Conflict Resolution Matrix**: See [`adoption/conflict-resolution.md`](./adoption/conflict-resolution.md).
- **Capability & Fallback Matrix**: See [`adoption/capability-matrix.md`](./adoption/capability-matrix.md).
- **Post-Adoption Verification Checklist**: See [`adoption/post-adoption-checklist.md`](./adoption/post-adoption-checklist.md).
